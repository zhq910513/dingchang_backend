## 页面与接口

前端页面：`/orders/create`、`/orders/:id` 编辑保存、订单导入完成保存。

后端接口：

| 接口 | 用途 |
| --- | --- |
| `POST /orders/draft` | 创建订单草稿 |
| `POST /orders/finalize` | 保存上传图片、动态字段、订单信息并触发 OCR |
| `POST /orders` | 传统创建订单 |
| `PUT /orders/{order_id}` | 编辑订单详情 |
| `PATCH /orders/{order_id}/status` | 完成/状态切换 |

本轮未修改数据库字段，未修改前端布局样式。

## 已发现问题与处理

| 编号 | 问题 | 风险 | 处理 |
| --- | --- | --- | --- |
| ORDER-SAVE-001 | `POST /orders/finalize` 和 `PUT /orders/{id}` 在动态字段变更时会同步一次查询投影，函数末尾又无条件同步一次 | 同一保存请求最多写两次 `order_fact_new`，增加写入锁竞争和提交前耗时 | 移除中途同步，保留末尾统一同步，兼容旧数据补偿 |
| ORDER-SAVE-002 | `dynamic_data` / `ocr_raw_json` 缺少后端大小上限 | 前端异常或恶意请求可提交超大 JSON，拖慢清洗、投影同步和数据库写入 | 增加写入保险丝：`dynamic_data` 最多 200 键/10 万字符；`ocr_raw_json` 最多 1000 键/100 万字符 |
| ORDER-SAVE-003 | 查询投影写入由多个入口触发 | 若实现分叉，会造成列表搜索字段漂移 | 创建、编辑、finalize、OCR worker 均收敛到 `sync_order_fact_from_dynamic_data` |

## 残余风险

1. 订单保存成功后仍会返回完整 `OrderOut`，这是现有前端详情页交互需要；若未来创建后只跳转列表，可新增轻量保存接口减少一次详情加载。
2. `ocr_raw_json` 上限按当前 OCR 结果结构预留较大空间；如果未来更换 OCR 供应商并返回更大结构，需要重新评估阈值。
