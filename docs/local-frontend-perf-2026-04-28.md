# 本地前端真实访问性能实测

测试时间：2026-04-28  
测试范围：前端页面真实打开、前端同源请求、后端 API 计时  
测试目标：确认列表页及核心业务接口响应速度，定位前端列表卡顿的真实来源

## 测试口径

1. 后端通过 `scripts/perf_server.py` 以本地性能模式启动，在 ASGI 中间件层记录 `/api/*` 的服务端耗时。
2. 前端通过 Vite 本地服务打开 `http://127.0.0.1:5173`，浏览器中注入临时本地测试 session，不绕过前端路由。
3. 页面实测打开以下路由各 3 轮：订单全部、已完成、未完成、导入、新建、订单详情、财务列表、财务详情、用户、客户渠道、渠道、AI 助手。
4. 同源请求实测通过前端域名发起 `fetch('/api/...')`，经过 Vite proxy 到后端，避免直接命中后端造成口径偏差。
5. 本轮只测安全 GET 接口；写入、删除、OCR 上传、外部 AI 调用等非幂等或外部依赖链路未在本轮压测中触发。

## 卡顿原因判断

1. 订单列表本体不是当前主要卡点。`GET /api/orders` 在隔离复测下 P95 为 32.258ms，真实页面路由 P95 为 63.962ms，尖峰来自页面初始化阶段的并发接口。
2. 前端感觉卡顿更可能来自“页面启动请求簇”：订单列表、团队、业务员、字段配置、total-only 统计会在短时间内并发触发，单个接口虽然快，但并发下会出现 70-90ms 的尖峰。
3. 当前最慢的真实接口是 `GET /api/finance/orders/export`，全量导出已完成订单并生成约 2.5MB 文件，平均 1092ms。该链路不是普通列表首屏卡顿来源，但属于后续必须重点优化的重接口。
4. `GET /api/orders/customer-groups` 是旧全量下拉接口，返回体积约 71KB，P95 134.813ms。新页面热路径已使用分页接口 `GET /api/customer-channel/customers`，后者 P95 13.261ms。
5. `GET /api/field-config/form-config` 是多页面共用的表单配置热路径，隔离状态可接受；真实路由下偶发 87.704ms，后续可继续做本地内存缓存和版本失效控制。

## 后续优化优先级

| 优先级 | 事项 | 原因 | 建议方案 |
| --- | --- | --- | --- |
| P0 | 保持订单列表读模型和权限裁剪 | 列表已进入稳定区间，不能为“再快一点”牺牲权限边界 | 继续以角色数据域为第一约束，只优化 SQL 和返回字段 |
| P1 | 财务导出异步化或流式化 | 当前唯一秒级接口，数据增长后会成为明显瓶颈 | 保持现有字段不变，改为后台任务生成文件或服务端流式响应 |
| P1 | 废弃或分页化 `/api/orders/customer-groups` | 旧全量接口返回体积偏大 | 前端继续走分页搜索接口；旧接口保留兼容但逐步减少调用 |
| P2 | 表单配置缓存 | 多页面首屏都依赖该接口 | 按 `module + role` 做短 TTL 缓存，字段配置变更时主动失效 |
| P2 | 页面启动请求去重 | 并发请求簇是前端感知尖峰来源 | 不改布局样式，仅在数据层做缓存、取消重复请求、共享字典请求 |

## 本轮结论

本地真实前端访问证明：列表页卡顿的主要矛盾已经不是单个列表 SQL，而是页面启动阶段多个接口同时触发导致的尾延迟；核心列表接口 P95 已控制在 30-65ms 区间。下一轮应该优先处理财务导出、旧全量下拉接口、字段配置缓存和前端数据请求去重，继续保持“不改库表字段、不改前端样式布局”的边界。
